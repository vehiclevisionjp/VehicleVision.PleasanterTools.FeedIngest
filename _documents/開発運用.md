# 開発運用

## ブランチと PR

- `develop` が開発の本流、`master` がリリース確定用
- 作業ブランチは `develop` から分岐し、PR の base も `develop`
- Issue を作ってから変更し、PR 本文に `Closes #N` を書く
- 作業中は Draft とし、タイトルに `WIP:` を付ける。Draft 解除はレビュー可能、`WIP:` 除去はマージ可能の合図

## 定期実行

| 対象 | 頻度 | 仕組み |
| --- | --- | --- |
| Pleasanter 参照ソース（サブモジュール）の最新化 | 毎日 | `reference-submodule-update.yml` が上流の `Pleasanter_*` 最新タグと比べ、遅れていれば Issue と Draft PR を作る |
| npm・NuGet の patch 更新 | 毎日 2 回（09:00 / 21:00 JST） | `patch-updates.yml` が最新 patch を適用して `master` へ PR を作り、必須チェックが通れば自動マージ。続けて `patch-updates-sync.yml` が `master` → `develop` の同期 PR を作り自動マージ |
| Actions の更新 | 毎週 | Dependabot（`.github/dependabot.yml`）が `develop` 向けに PR を作る |
| 依存の脆弱性検査 | 毎週月曜と push | `dependency-audit.yml` |
| CodeQL と依存レビュー | 毎週日曜と push／PR | `codeql.yml`、`dependency-review.yml`。public か GHAS 有効のリポジトリだけで動く（下記） |

参照ソースの更新 PR は、サブモジュールのポインタだけを進める。`_reference/README.md` や `_documents/アーキテクチャ方針.md` が書いている「根拠にした版」は自動では書き換えない。新しい版で確認し直してから揃える。

## GitHub の初期設定

新しいリポジトリを作った直後に行う。

1. 既定ブランチを `develop` にする
2. **リポジトリの設定を、全リポジトリと同じにする。** 定義は `.github/repo-settings.json`、反映は `./scripts/Sync-RepoSettings.ps1`（管理者権限が要る）。
   マージ後にブランチを削除する・自動マージを許可する・ブランチ更新のボタンを出す。マージ方式は squash と merge commit だけ（rebase は使わない）。
   Wiki・Projects・Discussions は使わない（内容は `_documents` に置く）。依存グラフと Dependabot アラートも有効にする
   （無いと依存レビュー `dependency-review` が失敗する）。**public** のリポジトリでは、シークレットスキャン・プッシュ保護・
   Dependabot のセキュリティ更新は**使わない**（patch 更新は自前のワークフローで行う）。シークレットスキャンとプッシュ保護は、internal / private では GitHub Advanced Security が要るので対象外
3. **ルールセットを設定する。** 定義は `.github/rulesets/` の 3 つ、反映は `./scripts/Sync-Ruleset.ps1`（管理者権限が要る）。
   全リポジトリで同じ形にしている（2026-10-20 に統一した）。リポジトリの管理者は迂回できる（初期配置と緊急対応のため）
    - `develop-protection`: develop。削除と強制 push を禁止し、必須チェックを要求する
    - `master-protection`: master。上に加えて PR を要求する
    - `release-tag-protection`: タグ `v*`。削除と強制 push を禁止する
    - 必須チェックの既定は `build-test`、`instructions`、`nuget-audit`、`npm-audit`、`wip-title`。
      CodeQL を動かすリポジトリでは `-IncludeCodeQL` で `Analyze (csharp)` も必須にする。
      そのリポジトリ固有のジョブ（例: `integration`）は `-ExtraChecks` で足す（**CI のジョブ名と同じ文字列**）。
      **必須にしないと、失敗してもマージできてしまう**
    - 旧い形（develop と master を 1 つにまとめた「保護ブランチ」）が残っていれば、スクリプトが新しい 3 つを作ってから消す
4. 参照ソースの更新用に GitHub App を使う。リポジトリ変数 `MY_REPO_AUTOMATION_BOT_CLIENT_ID` とシークレット `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` を登録する。App には Contents・Pull requests・Issues の書き込み権限が要る
5. 公開範囲に応じて CodeQL と依存レビューを切り替える。**public** のリポジトリは何もしなくてよい。**internal / private** は、コードスキャンと依存レビューに GitHub Advanced Security（GHAS）が要る。GHAS を有効にしたら、リポジトリ変数 `CODEQL_ENABLED` を `true` にする（`gh variable set CODEQL_ENABLED --body true`）。有効にしない間、この 2 つのジョブはスキップされ、リリースの確認もスキップを許容する
6. ラベルを作る。定義は `.github/labels.json`、反映は `./scripts/Sync-Labels.ps1`（gh CLI でログイン済みであること）。参照ソース更新の Issue は `1-owner:automation`、`2-type:dependencies`、`3-area:pleasanter` を使うため、無いと作成に失敗する
7. 「Template repository」にするのはテンプレート側のみ。派生したリポジトリでは外す

## FeedIngest の初期設定状況

2026-10-22 に既定ブランチ `develop` と Public・非テンプレートを確認し、
Sync-RepoSettings・Sync-Ruleset（IncludeCodeQL）・Sync-Labels を適用した。
3ルールセットと24ラベルを反映済み。CLA 必須チェックは存在しない。
GitHub App 用の変数・秘密は登録されていない。実値の提供・App の導入は運用者の作業とする。
値を推測して登録したり、別リポジトリから転記したりしない。
そのため参照ソース更新・patch 自動更新の実行は未確認。通常のCIは初期化コミットで成功を確認した。

## 外部記憶

Claude や Codex が作業の知見を残す必要があるときは、`<リポジトリ名>.ClaudeMemory` の名前で Internal リポジトリを作って管理する。本体リポジトリへ記憶ファイルを置かない。

- 作ったら `CLAUDE.md` に URL を書く
- 作業ツリーはエージェントのメモリディレクトリそのものにし、別の clone を作らない（2 つあると片方が古くなる）
- 正式な規約の置き場所ではない。`.github/copilot-instructions.md` が常に優先され、食い違ったら記憶側を直す

## patch 更新の自動適用

- 対象は同じ major.minor の最新の安定版だけ（minor・major は人が見る）。プレリリース版と非推奨の版は選ばない。
- 検出と適用は `scripts/apply-patch-updates.mjs`。版・ロックファイル・NOTICE を 1 つの PR に揃える。`--dry-run` で検出だけ試せる。
- PR と push は `my-repo-automation-bot`（GitHub App）のトークンで行う。`GITHUB_TOKEN` だと CI が動かず、必須チェックが付かないため。
  変数 `MY_REPO_AUTOMATION_BOT_CLIENT_ID` とシークレット `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` が要る（権限は contents と pull-requests の書き込みのみ）。
- 前回の PR が開いたままなら、新しい PR は作らない。CI が落ちたら自動マージされず PR が残るので、人が見る。NOTICE が自動で直せないときは PR を作らずに失敗する。
- 更新したくない依存は `.github/patch-updates-ignore.txt` に 1 行 1 名で書く（`#` から行末はコメント）。
- 前提: リポジトリの設定で自動マージ（`allow_auto_merge`）を許可し、`master` の必須チェックを設定してあること。

## patch 更新だけが溜まったときの自動リリース

- `patch-release.yml` が、毎日 2 回（11:00 / 23:00 JST。patch 更新の 2 時間後）、最後の安定版タグ以降の `develop` を調べる。
- patch 更新のコミットが 1 件以上あり、**それ以外のコミットが無い**ときだけ、`release-run.yml` を `patch`・`dry_run=false`・`acknowledge=true` で起動する。
  採番・版の引き上げ・`develop` → `master` の PR・タグ付けは、`release-run.yml` が行う。
- 差分が無ければ何もしない。人が入れた未リリースの変更が混ざっているときも自動では出さない（人が内容を見て手で起動する）。
- 動かない条件: 安定版のタグがまだ無い（最初のリリースは人が行う）、`release-run.yml` が無い、リリースが実行中・PR が開いたまま。
- 自動リリースの対象外: Core（プレリリース版のタグ）、IndexCreator・CalendarStyleCreator（`release-run.yml` が無い）。
