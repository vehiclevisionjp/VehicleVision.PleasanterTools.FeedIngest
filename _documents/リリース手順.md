# リリース手順

## 版

版の単一情報源は `Directory.Build.props` の `VersionPrefix`。セマンティックバージョニングに従い、1.0.0 未満は互換を保証しない。

## 手順

1. `develop` で `VersionPrefix` を上げ、`master` へ PR を出してマージする
2. Actions の「リリースタグ作成」を `master` から実行する。最初は `dry_run` のまま版だけを検証する
3. 問題なければ `dry_run` を外して実行する。必須チェックの成功を確認してから、GitHub App のトークンで `vX.Y.Z` タグを作る
4. タグを契機に「Release」ワークフローが、検証、配布 ZIP と SHA-256 の作成、GitHub Releases への公開を行う

`vX.Y.Z-rc.1` のようにハイフン付きの版はプレリリースとして公開する。

## 公開前の確認

- `LICENSE` と `NOTICE` が現状と合っている
- 配布物に設定ファイル・秘密・参照ソース・Git メタデータが入っていない
  （`scripts/package.ps1` が `_reference`・`.git`・`.gitmodules` 等を検査する）
- 参照ソースは AI が必要時に取得するだけで、CI・リリース時の取得は行わない
- [ライセンス](ライセンス.md) のデュアルライセンスの提供条件と第三者表示を確認している
- `LICENSE-COMMERCIAL.md` の連絡先が記入済みである

## 移行・注意

本番の状態 DB の移行は自動では走らない。更新後に利用者が `migrate-status` で未適用を確かめ、`migrate` を実行する（[README](../README.md) の「状態 DB」）。
リリースノートの「移行・注意」には、その版で増える移行を書く。共通部品 Core.Data の版を上げたときは、共有移行（`Core_` の表）が増えるかを Core の公開内容で確かめて書く。

- Core.Data 0.3.0 を取り込んだ版から、共有移行 M10008・M10009 が増える。空の表 `Core_AdminPasskeys`・`Core_AdminPasskeyChallenges` を作り、`Core_AdminSessions` に NULL 可の `Via` 列を足す。`migrate` を実行する DB ユーザーに、表の作成と列の追加の権限が要る
- 確認の記録: 2026-11-26 に、SQLite・PostgreSQL 17・MySQL 8.4・SQL Server 2022 で、0.2.0 の状態 DB を 0.3.0 で `migrate` し、M10008・M10009 の適用と、表と列の作成を確認した（SQLite は表と列まで直接確認。他の 3 つは `migrate` の適用結果と `migrate-status` の完了まで）
