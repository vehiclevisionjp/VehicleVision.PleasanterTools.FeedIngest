# 対応づけ設定（設計案）

2026-10-22、Issue #1。**この JSON を読む機能は未実装**。
全体の前提・未決事項は [アーキテクチャ方針](アーキテクチャ方針.md) を参照する。

## 1. 設定の形

1取り込み元ごとに、安定した `id`、取得先、認証、取り込み先サイト、
予約外部キー列、項目から列への対応づけを宣言する。
秘密値ではなく環境変数名を参照する。以下に実在する秘密は含まない。

```json
{
  "schemaVersion": 1,
  "pleasanter": {
    "id": "office",
    "baseUrl": "https://pleasanter.example.test",
    "apiVersion": 1.1,
    "apiKeyEnv": "FEEDINGEST_PLEASANTER_API_KEY",
    "apiKeyUserTimeZoneId": "Asia/Tokyo"
  },
  "sources": [
    {
      "id": "vendor-news",
      "url": "https://feeds.example.test/news.xml",
      "format": "auto",
      "http": {
        "timeoutSeconds": 30,
        "maxRedirects": 5,
        "maxBodyBytes": 10485760,
        "authentication": {
          "type": "basic",
          "usernameEnv": "FEEDINGEST_VENDOR_USER",
          "passwordEnv": "FEEDINGEST_VENDOR_PASSWORD"
        }
      },
      "target": {
        "siteId": 12345,
        "externalKeyColumn": "ClassZ",
        "mode": "upsert"
      },
      "mapping": [
        { "target": "Title", "source": "title", "default": "（無題）" },
        { "target": "Body", "source": "contentText", "onMissing": "omit" },
        { "target": "ClassA", "source": "link" },
        { "target": "ClassB", "source": "categories", "transform": "join", "separator": ", " },
        { "target": "ClassC", "constant": "vendor-news" },
        { "target": "DateA", "source": "publishedAt", "onMissing": "omit" },
        { "target": "DateB", "source": "updatedAt", "onMissing": "omit" },
        { "target": "DescriptionA", "source": "summaryText" },
        { "target": "DescriptionB", "source": "enclosures", "transform": "json" }
      ]
    }
  ]
}
```

`format` は `auto` / `rss20` / `atom10`。auto は対応する2形式だけを判定する。
`target.siteId` は正の64bit整数。APIキー利用者に、そのサイトの参照・検索・作成・更新権限が必要。
JSON の未知プロパティ、重複プロパティ、同じ source ID、未知の enum 値はエラーにする。
sourceごとの送信先は、この版ではルートの pleasanter 1つのみ。
複数の Pleasanter インスタンスへ送る場合は、別の設定・実行として状態を明示的に区切る。

### ヘッダ認証の代替例

Basic の代わりに `authentication` だけを次の形に置き換える。
値は Bearer等の接頭辞を含めて秘密ストアが供給する。値をJSON内で組み立てない。

```json
{
  "type": "headers",
  "headers": [
    { "name": "Authorization", "valueEnv": "FEEDINGEST_VENDOR_AUTHORIZATION" },
    { "name": "X-Feed-Token", "valueEnv": "FEEDINGEST_VENDOR_TOKEN" }
  ]
}
```

認証なしは `{ "type": "none" }`。Basic／headers を同時に定義しない。
環境変数 `FEEDINGEST_VENDOR_TOKEN` の代わりに
`FEEDINGEST_VENDOR_TOKEN_FILE` で秘密ファイルの絶対パスを指定できる設計。
両方を指定したらエラー。JSON中の `valueEnv` は `_FILE` を含まない基底名で統一する。

## 2. 元項目の公開名と変換

| source | 型／意味 |
| --- | --- |
| title | 文字列。HTMLならテキストへ変換 |
| link | 解決済みの絶対 URI の文字列 |
| contentText / summaryText | 未信頼HTMLを実行せずテキスト化した本文／要約 |
| publishedAt / updatedAt | オフセット付き日時または欠落 |
| categories | 正規化カテゴリの表示文字列配列。元の順序を維持 |
| authors | 名前の配列。アドレスの自動送信はしない |
| enclosures | URL・type・length のオブジェクト配列。ファイル実体ではない |
| nativeId | 元の guid/id（URLとは限らない）。任意の監査列へ保存可能 |
| sourceId | 安定した取り込み元ID |

`source` と `constant` は排他。default は source の欠落・null・空文字・空配列のときだけ使う。
false・0 は有効値。既定値を置いても型変換失敗・文字数超過を救済しない。
constant と default を同時に置く設定はエラー。
default が無い場合、`onMissing` は `omit`（既定）または `error` を選べる。
空文字を明示設定する constant は列のクリアとして扱うが、日付クリアは初回非対応。

変換は scalar の identity、配列の join、メタデータ配列の json だけを初回候補にする。
categories／authors の配列をそのままClassへ渡す設定はエラーにする。
join は `separator` を必須にし、空要素を除去した順序を固定する。
json は invariant な直列化で、URL・type・length のみを含む。秘密ヘッダは含めない。
出力は同じ入力・同じ設定版から常に同じ値。現在時刻・乱数・ネットワーク参照を使わない。

**テンプレート式・文字列補間・任意コード・JavaScript は初回非対応。**
`template` / `script` の指定や、未定義変換を黙って無視せず設定エラーにする。
本文そのものにある `{{...}}` 等を式として評価しない。
Q の高度なスクリプトエンジンは持ち込まず、実需があれば別途設計する。

## 3. Pleasanter の列への変換

| target | Pleasanter API の形 | 初回の扱い |
| --- | --- | --- |
| Title / Body | レコード本体の同名プロパティ | 文字列 |
| ClassA… | ClassHash.ClassA… | 単一文字列。外部キー列を除く |
| DateA… | DateHash.DateA… | APIキー利用者のタイムゾーンで変換 |
| DescriptionA… | DescriptionHash.DescriptionA… | 文字列、enclosureのJSONも可 |
| NumA… / CheckA… | NumHash / CheckHash | 型を明示検証した数値／真偽の固定値等 |
| AttachmentsA… | AttachmentsHash.AttachmentsA… | 初回は拒否。次段階の拡張点 |

`ClassA` 等は表示ラベルでなく内部列名。A〜Zを基本とし、001等の拡張列はサイト検査で確認する。
同一 target の二重定義、予約外部キー列、ID・SiteId・Creator等のシステム列への割当は拒否する。
外部キーは対応づけ後に別枠で注入し、固定値や既定値で上書きさせない。
APIの Num／Check 固定値は文字列でなく JSON number／boolean を使う。
Title等の文字数、Classの選択肢、Dateの範囲はサイト制約に合わせる。
切り詰め・不正値の無断null化はしない。検証不能な制約は未確認として診断する。

API 出力の形は次の例。ApiKey の実値は送信直前だけに注入し、この設定やログには保持しない。
この JSON は説明用で認証情報が無いため、そのまま送れるリクエストではない。

```json
{
  "ApiVersion": 1.1,
  "Title": "記事タイトル",
  "Body": "テキスト化した本文",
  "ClassHash": {
    "ClassA": "https://news.example.test/items/42",
    "ClassC": "vendor-news",
    "ClassZ": "fi:v1:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  },
  "DateHash": {
    "DateA": "2026-10-22T09:00:00"
  },
  "DescriptionHash": {
    "DescriptionA": "要約",
    "DescriptionB": "[]"
  }
}
```

日時の例は Asia/Tokyo 基準。実機での書式・解釈は未確認であり、仕様の動作確認結果ではない。
Q の変換設計と Pleasanter 固定ソースのフィールド名だけを根拠とする。

## 4. 添付の段階分け

第2段階は enclosure の URL・MIME type・宣言サイズを保持／対応づけるまで。
length の宣言値を信頼して実体取得しない。`enclosures` の URI は参照先として保存するだけ。

次段階でバイナリを扱う場合は、対応づけを通常の文字列と別の attachment 指示へ拡張する。
Q と参照ソースの事実として、API の追加項目は `Name / Base64 / Added`、
削除には `Guid / Deleted` の形があるが、FeedIngest の実機では未確認。
URLの内容が変わった場合の添付識別・内容ハッシュ・追加重複・削除・結果不明を別途設計する。
既存添付を空配列で消せると仮定せず、未検証の自動削除を入れない。
ファイルサイズ・合計容量・型の許可リスト・宛先制限・検査方式を承認してから追加する。

## 5. メールとの境界

「同じメールを二重作成しない」ことは MailIngest 側でも必要だが、本設定はフィード専用。
概念上は安定した source ID と外部キー列・配送状態を使い、POP3のUIDL、
IMAPのUIDVALIDITY＋UID、Message-ID の長所と欠落・再利用を MailIngest で比較すべき。
Message-ID や件名だけで一意になるとは仮定しない。
メール用項目名・メール本文・添付・受信後削除の規則は、FeedIngestへ混ぜず別設計にする。
